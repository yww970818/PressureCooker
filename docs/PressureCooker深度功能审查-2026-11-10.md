## 2. 已确认并修复的问题

### F1：超时配置可接受 NaN、Infinity、溢出与不足 1ns 的数值

位置：`controlplane/manager-go/config.go:60`，`envDuration`。

原实现只检查解析失败或 `<=0`，NaN 不满足该比较，正无穷和大数也会进入 `time.Duration` 转换，产生零或不可用的时长。现只接受有限、正数且纳秒值可表示的配置，错误在启动阶段返回，不延迟到连接或调度运行中。

回归覆盖非法值与合法边界，记录见 `regressions-red.log`、`regressions-green.log`。

### F2：损坏的 WebSocket 声明会静默换成默认连接

位置：`workflow_websocket.go:127`、`workflow_compile.go:272`、`workflow_components.go:381`，均在 `controlplane/manager-go/`。

原实现对 Base64/JSON 解码失败返回默认配置，可能使导入、修改后发布的执行目标和用户原声明不同。现区分“声明不存在”与“声明已存在但损坏”：已有 authored 字段即使为空也不能回退；缺少 authored 字段但有合法执行配置时仍可读取。损坏 Base64、非法 JSON、null、数组与不支持动作均明确拒绝导入或编译，不改写已保存数据。

回归还覆盖从 `raw_xml` 编译的路径，防止仅修复导入入口而留下发布路径。记录见 `regressions-red.log`、`regressions-green.log`、`regression-race.log`。

### F3：扩展引用统计只检查普通列表的前 200 个流程

位置：`controlplane/manager-go/workflow_extensions.go:215`，`workflowExtensionUsage`。

统计原来复用普通列表接口，其默认上限为 200，较早流程使用的组件可能被误报为没有引用。现使用项目内、未删除流程的 ID keyset 扫描，每批 32 条，读取后关闭 SQL 游标再解密；遵守取消信号，保留不透明 XML 子树内的组件统计。普通列表上限没有放大。

回归使用 205 个流程及仅存在于最早流程的组件；同时检查项目过滤和取消。记录见 `regressions-red.log`、`regressions-green.log`、`related-integration.log`。

### F4：Redis owner 恢复错误依赖默认项目存在

位置：`controlplane/manager-go/runner_recovery.go:132`。

恢复事务锁定 `project-default` 行；恢复后的数据库若只有明确的其他项目，会得到 `sql.ErrNoRows`，失效 owner 不能完成终结。现与集群修改、任务领取使用同一平台级互斥 `lockClusterConfigurations`，锁定稳定迁移账本行，与用户项目生命周期解耦。

在隔离 MySQL 中复现并修复；相关锁等待取消、观察 epoch 与 fencing 测试一起通过。阻塞测试更新为锁同一互斥对象。记录见 `recovery-red.log`、`recovery-green.log`、`regression-race.log`。

### F5：按普通变量名称猜测并重写服务地址

位置：`controlplane/frontend/src/api-management/environments.js:31`。

原逻辑将 `url`、`existingurl`、`baseUrl`、`baseURL`、`基础地址` 变量复制成 `base_host`。这些名称可能是普通业务参数，平台不能靠名称推断用途。现只使用显式 `base_host` 或调用方提供的合法 OpenAPI 服务地址建议，普通变量按原内容保留；没有地址时由通用表单要求用户填写。

更新原测试预期，增加独立回归。记录见 `environment-target-red.log`、`environment-target-green.log`、`frontend-full.log`。

### F6：部署中的六节点布局成为平台身份与数量限制

位置：`controlplane/manager-go/clusters.go:99`、`cluster_defaults.go:13`、`config.go`，`controlplane/mcp-go/manager_tools.go:57`、`platform_tools.go`，及前端 MCP 参数说明。

原管理端只接受 `worker-1` 至 `worker-6`，MCP 固定枚举相同节点；同时根据“两个 Core、六个 worker”自动猜测 2/4 分组。执行协议实际已支持通用 ID 和 64 个节点，导致合法扩容在上层被拒绝。

现采用执行协议的通用 ID 校验，仍必须在可信部署清单和所选集群中存在且不得重复；数量与 `protocol.MaxNodeReportWorkers` 统一。由于当前每个 Core 获取完整 worker 探测清单，部署总 worker 数也限定为 64，并在启动时拒绝超限或非法 ID。**本轮没有实现无限节点注册或超过 64 的分片发现。**

源码不再内置两个 Core/六个 worker 的地址清单，不按数量猜测分区。标准 Compose 继续显式声明原地址和 2/4 映射；已保存集群与已冻结任务快照优先，不被重排。原生启动应显式配置地址与映射；缺少映射时原共享池行为仍存在，见 D7。

新增 64 节点边界、非法/重复/未注册节点、禁止猜测拓扑、7 个自定义节点提交及快照、忙碌成员保护回归；MCP 实际工具目录夹具由 Go/官方 Node 工具表重新生成。记录见 `node-topology-red.log`、`node-topology-green.log`、`node-topology-integration.log`、`node-topology-race.log`、`node-catalog-update.log`。

## 3. 实施前结构性问题（历史记录）

以下为实施前的问题、证据和方案，保留用于追踪决策；其中旧路径及行号不再代表当前实现。当前落地情况和剩余边界以上文“实施复查更新”为准。

### D1 / P1：新 Redis 任务与旧 HTTP 执行链同时存在

证据：

- `store.go` 的 `createRun` 为新任务写入 `execution_mode=redis`。
- `scheduler.go:101` 对 Redis 和其他任务分流；`:226` 仍可挑选旧任务，`:360` 向控制器发送 `POST /runs`。
- 当前执行器 `execution/cmd/jmeter-executor/main.go` 没有该启动路由。旧记录进入 PREPARING 后可能反复失败，仍被视为活动任务，影响全局批次队列推进。
- `scheduler.go:500` 仍发送旧 `/reset`；执行器 `main.go:104` 和 `worker.go:278` 保留无 task/lease 的旧 reset 协议。它仍要求 bearer、无现有 owner、generation 匹配，不能描述为无限制的清理绕过。
- `scheduler_archive.go:54` 为旧任务后台扫描全部终态记录，随后才排除 Redis 任务；长期增加历史扫描成本。

处理方案：只保留 Redis outbox、签名快照、task/attempt/lease/epoch fencing 的执行状态机。将旧 HTTP 启动、调度、清理、孤儿认领、归档轮询、旧运行写接口和相应测试一起退出；不可只删一个路由。历史 JTL/HTML 读取、下载及显式导入独立保留，不获得重新执行能力。

切换前用只读审计列出旧非终态记录、owner 和外部进程。确认实际执行节点空闲后，通过可重入、带审计回执的一次性工具明确终结或转换元数据；不能在启动时偷偷把旧任务标完成，也不能把缺 lease 的任务伪造成新 attempt。新旧导入记录用明确的来源/格式字段区分，避免长期保留第二套执行开关。

验收：旧任务不能阻塞新队列；管理端不再调用旧启动/恢复路径；worker 清理一律校验任务归属；历史只读内容指纹不变；新链停止、失联、回调迟到和重复投递回归通过。

### D2 / P1：接口调试仍有两套可执行环境模型

证据：`api_operations.go:450` 起同时支持项目 `environment_id` 和集合 `environment` / `client.active_environment` / `x-scalar-environments`。MCP `manager_tools.go` 的 `debug_api_request` 仍公开两者。界面新模型已按稳定项目环境 ID 保存覆盖，但没有贯穿全部入口。

影响：HTTP、MCP、页面未显式选项目环境时，可能从旧字段选择变量和目标，地址来源难以判断；仅移除变量名猜测不足以结束双模型。

处理方案：调试命令声明 `target_source`，只允许 `project_environment` 或 `document_server`。前者必须给项目环境 ID，以固定环境地址、集合覆盖、单次覆盖的确定顺序解析；后者明确选择 OpenAPI server，保留通用文档直接调试能力。拒绝冲突参数和隐式活动环境。导入保留旧原文但不自动赋予执行语义，提供显式转换预览及新修订保存。

验收：每次调试能返回脱敏的地址来源与环境 revision；HTTP/MCP/UI 同输入同结果；旧字段不隐式改变目标；集合读取、保存与历史导出不受未知规则影响。

### D3 / P2：扩展“已安装”、编辑能力与运行能力未完全分层

证据：`workflow_extensions.go:79` 的目录为平台/原生组件返回 `installed=true`；描述明确说明这不代表远端 JAR 已核验。自定义定义及安装状态位于 `projects.data.workflow_extensions`，更新持有项目行锁，项目内上限 100。接口展示插件也存于项目状态。MCP 有接口插件工具，尚无对应完整流程扩展管理工具。

影响：用户可能将“可编辑”理解为“可执行”；多个插件更新相互串行，共享 JSON 不适合不可变版本、审计及节点差异能力。

建议新增独立模型（名称为建议，尚未建表）：

| 模型 | 关键内容与约束 |
| --- | --- |
| `extension_definitions` | project_id、extension_id、kind、不可变 version、schema_version、SHA256、加密定义；项目/ID/version 唯一 |
| `extension_installations` | 项目、扩展、明确版本、enabled、revision；独立乐观锁，不改写历史引用 |
| `runtime_capabilities` | node_id、runtime/build 摘要、能力 ID/版本、observed_at、expires_at、验证状态与脱敏失败原因 |
| 引用投影 | workflow_id、workflow_revision、extension_id/version 或不透明组件标识；随 authored 版本原子更新，可重建 |

编辑器状态表达为 enabled/definition_available；运行时能力单独表达 verified/unknown/unavailable，过期不视为通过。JS 画布适配器继续只生成编辑表单，展示插件继续只解释收到的帧；都不能发送消息或替代后端编译器。

协议扩展端口建议统一为 `Validate`、`Debug`、`Compile`、`Capabilities`，由实现显式注册支持能力。RPC/gRPC/Protobuf 描述保留为 reserved，未注册执行能力不能出现在可执行菜单或编译结果中。插件升级固定版本、失败可回退；未知历史引用按 AGENTS 惰性保留，可显式删除。

### D4 / P2：监控补充重复保存完整快照，分页仍全量解码

证据：`pressure_report_monitoring.go:356` 的写路径将完整快照插入 `pressure_report_metrics`；单快照上限 8MiB、最多 128 次修订、1000 个实例。`pressure_report_monitoring_batch.go:136` 没有分页参数时返回完整快照，有分页时也先解码全部实例后过滤。`frontend/src/reports/MonitoringCards.vue:8` 请求完整数据再交给页面展示。

影响：快照接近上限且每次小修改时，单报告快照累计理论上可接近 1GiB；批量写降低重复次数，但没有消除存储放大。客户端分页不能降低数据库载荷、后端解码及网络全量传输成本。

建议拆分不可变实例证据与修订成员关系：revision 元数据保存幂等键哈希、请求哈希、来源及时间；实例证据保存组件、稳定实例 ID、schema_version、内容哈希及正文；revision-membership 引用具体实例证据版本。相同证据按哈希复用。索引覆盖项目/报告/revision/component/instance，列表 SQL 分页并返回摘要，时序与日志按实例详情加载；完整快照仅由显式 export 组合。

保留原始证据、时间窗、采集来源和零/null 语义；外部监控不改写 JTL 指标与业务验收结论。迁移通过新表分批导入、每 revision 哈希核对、读链切换完成，不能丢弃旧 revision 或静默截断。

### D5 / P2：缺一份摘要会触发整个数据集目录的旧路径

证据：`dataset_management.go:265` 只要发现任意未删除流程 `summary_payload IS NULL`，就调用 `legacyDatasetManagementCatalog` 解密项目全部流程。与 `page_read_models.go` 对当前页缺失项批量回退不同，单个缺失会放大为全项目读取。

处理方案：查询中按缺失 ID 分批补读，正常流程继续走投影；将 `rebuild-read-models` 作为有进度、可取消、可重入的维护入口，提供投影覆盖率和错误计数。后续若决定停止旧格式运行读取，先完成显式重建验收，再删除该格式分支。

缺失、过期或损坏的可重建编辑缓存回退原载荷是合理恢复机制，不应只因名称含 fallback 就删除。F3 修复后的引用统计虽完整，结果总量仍随全项目引用增长；大型项目可复用版本化引用投影，避免每次反复解密。

### D6 / P2：身份字段已通用化，但领域命名仍绑定 Cookie

证据：`plan_cookie_accounts.go`、`jmeter.cookie_accounts`、`cookie_account.<身份名>.<字段>`、前端 task-cookie-accounts；`plan_cookie_accounts.go:143` 对非 cookie 类型明确拒绝执行。当前没有内置业务角色、字段用途或账号轮换，但模型名仍暗示平台只服务某类认证。

建议下一版发布声明采用 versioned script identities：字段 name/type/secret/required、身份名称与用途完全由脚本声明；实际如何将值写入请求由脚本负责。只有确实需要协议运行时协作时才增加带能力校验的认证适配器，不为了名称通用化虚构 OAuth/RPC 支持。

不可变 JMX 及其 SHA256 必须保留；通过显式再发布生成新声明、新属性命名和新计划指纹，不批量替换旧脚本前缀。旧报告和冻结属性只读保留。移除旧提交协议前先完成脚本升级清单与预览，避免 UI、MCP、任务执行器各用不同模型。

### D7 / P2：隐式项目与共享池默认仍影响归属

证据：`projects.go:157` 在缺少项目头时回落默认项目，`objectProject` 对缺少归属字段也回落；`clusters.go:27` 对没有显式成员映射的控制器仍继承全部已配置 worker，并标记 `legacy_shared_pool`。F6 已删除自动 2/4 猜测，但没有删除这项共享池行为。

建议项目资源 API 必须显式声明项目，下载由拥有者验证，默认项目仅用于显式 bootstrap/历史导入。部署映射缺失时显示“待配置”并禁止新任务领取，或要求显式声明 `shared_pool` 模式；不能靠缺字段授予整个池。导入/恢复提供归属预览，用户确认的新修订保存后才进入新执行模型。

当前平台是单管理凭据模型，不能把项目过滤描述成已具备多用户 RBAC。若将来需要多人权限，应以 principal/project/permission 在入口集中授权，领域仓储仍按项目查询，避免复制出多套权限分支。

## 4. 模块及表设计的收敛路线（初审方案）

现有 `internal/tasks`、`internal/nodes`、`internal/workspace`、`internal/interfaceprotocol`、`internal/schema` 已提供领域边界。建议在一个管理端内继续按功能组织应用服务，无需为清理债务引入微服务：

1. TaskService 负责提交、冻结快照、outbox、终态；RecoveryService 复用同一 owner/fencing 协议。Scheduler 仅驱动当前状态机，历史导入另设工具。
2. EnvironmentResolver 接受显式 target source 和固定 revision；HTTP、WS、编译、MCP 通过同一入口获得脱敏来源信息。
3. ExtensionRegistry 管理不可变定义、安装版本和 runtime capabilities；展示/编辑/执行端口分别注册。
4. ReportService 保持 JTL、独立线程观测、外部监控证据来源分明；MonitoringRepository 负责 SQL 分页和不可变证据。
5. WorkspaceRepository 负责载荷加密、项目过滤和读模型；缓存重建是明确维护操作。`workspace_store.go:180` 的无 Context 旧 QueryRow 适配器优先收窄到测试或更小接口；生产 Database/Tx 当前有 Context，不能据此声称生产请求都忽略取消。

建议实施顺序：

| 阶段 | 范围 | 退出条件 |
| --- | --- | --- |
| A | 旧执行链退役、非终态旧记录审计与显式处理 | 新任务只有一种状态机；旧资料只读；无无归属清理路径 |
| B | 单一目标来源、项目/集群显式归属 | UI/HTTP/MCP/编译解析一致；缺失和冲突明确拒绝 |
| C | 独立扩展模型、能力探测及固定版本引用 | 编辑可用与运行验证分离；未知引用不执行、不丢失 |
| D | 监控证据规范化、SQL 分页、投影局部修复 | 大项目读取成本受页面大小约束；revision 证据哈希一致 |
| E | 身份声明新版及模块接口收窄 | 新发布用通用模型；旧不可变发布仍可审计 |

新增表应使用后续迁移编号；当前冻结迁移为 001–008。不要改写旧迁移校验和、历史发布路径、指纹和回执。DDL/回填分离，支持部分成功后重试；新格式切换前完成空库、旧库、失败重入、单连接池、项目隔离、备份恢复验收。旧执行清理和格式转换应是一次性工具，避免长期双写、双执行和按错误猜测旧模型。
