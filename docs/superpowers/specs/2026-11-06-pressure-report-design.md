# 压测报告入库与中文报告页设计

日期：2026-11-06。状态：用户已在本会话选择“按此设计直接实现”，设计已确认；任务详情大弹窗为用户已明确指定的独立调整，先行实现。

## 用户要求与已确认事项

- 管理平台收到任务结束回调后，下载压测原始报告和执行日志，解析为不同数据库字段，供自定义报告页读取。
- 页面面向非开发、非测试人员，解释这次测了什么、实际表现、目标是否达到、发现了哪些问题及依据。
- 预留后续 JVM、中间件、K8s 指标及 AI 分析结果入库和展示的能力。
- 每次压测可设置目标；没有目标时不作达标判定。此项已由用户于本会话确认。
- 任务与历史的查看详情改为大弹窗，不再在列表下面展开。详情、执行日志、原始文件及停止入口继续可用。
- 延续现有技术约束：前端 Vue、后端 Go、MySQL 和 MinIO；保留现有原始文件，不生成 JMeter HTML 报告，不新增 reporter 容器。

## 现状与接入位置

`manager-go/runner_http.go` 的 `runnerCallback` 已校验回调身份、事件幂等、任务归属及 MinIO 对象元信息，并在事务中保存任务终态和 `raw_archive`。原始文件是 `results.jtl`、`jmeter.log`、`console.log`。

旧 `reports` 表及 `/api/reports` 是历史产物接口，新生成已退役；启动时会将旧表未完成的报告改为失败。新功能使用独立 `pressure_*` 表和 `/api/pressure-reports`，避免改变历史报告或被旧迁移逻辑终止。

`RunDetail.vue` 当前只有概览、日志和原始文件，`Runs.vue` 将其放在列表下。新增报告入口和大弹窗使用同一个任务标识及当前项目隔离规则。

## 处理方式

采用 manager 内的 Go 后台分析任务，任务与结果持久化在 MySQL。已有部署不增加服务。

比较过的方式：

1. 在回调请求内同步下载解析：实现简单，但大文件、网络重试和数据库写入会延长回调，增加重复回调及任务终态处理风险，因此不采用。
2. manager 内持久化后台任务：复用既有存储和服务生命周期，可重试、恢复、查看状态，符合现有少服务部署约束，采用此方式。
3. 独立 reporter 服务：可独立扩缩容，但当前用户此前已移除该服务，首版不引入。

流程：收到有效结束回调 → 在同一事务中登记报告分析任务 → 回调快速返回 → 后台领取任务 → 从已验证的 MinIO 对象下载 → 校验实际字节数和 SHA256 → 解析与汇总 → 原子发布完整报告版本 → 页面读取结构化数据。

重复回调不会重复创建分析任务。唯一任务键固定项目、执行批次、来源指纹、解析规则和评审版本；回调事件保持已有幂等约束。后台失败不改变原任务执行结果；任务完成和报告就绪分别展示。进程重启、租约过期或临时 MinIO 故障后可恢复与重试。领取、续租、失败和发布都校验当前领取代次，过期领取者不能写结果。历史任务通过明确的“生成报告”操作进入队列，部署时不扫描并自动解析全部历史文件。

## 数据模型

常用的筛选、排序、展示和统计值使用独立列；变化较大的证据维度和扩展内容使用带版本的 JSON。不是把整份报告原文放进一个 JSON 字段后让前端自行解析。

| 表 | 主要内容 |
| --- | --- |
| `pressure_reports` | 项目、任务、执行批次、报告版本、解析器版本、状态、数据完整度、起止时间、采样数、成功/失败数、成功率、每秒执行数、平均/最小/最大耗时及 P50/P90/P95/P99、目标快照、判定结果 |
| `pressure_report_jobs` | 来源文件指纹、排队/执行/重试状态、领取者、租约、尝试次数、下次重试时间和安全错误码 |
| `pressure_report_sources` | 文件类型、MinIO bucket/key、字节数、SHA256、下载和解析状态、有效与无效记录数、来源范围及版本 |
| `pressure_report_steps` | 各接口或步骤的独立统计、失败原因、响应码分布、执行次数和延迟分布口径 |
| `pressure_report_timeline` | 分时请求量、失败量、耗时及数据覆盖信息；每个时间桶明确起止时间和宽度 |
| `pressure_report_issues` | 请求失败聚类、执行日志级别/组件/异常类型、首次/末次出现时间、次数、脱敏摘要及来源文件行号 |
| `pressure_report_metrics` | 可扩展指标：来源种类、服务/实例维度、指标名、单位、时间、值及结构化补充字段，供后续 JVM/中间件/K8s 接入 |
| `pressure_report_findings` | 规则或后续 AI 的结论、建议、级别、证据引用、来源、模型与提示词版本、分析时间；事实与推断分开记录 |

是否拆分来源记录和指标点的进一步索引由实现时按查询确定，但项目、任务、报告版本、来源种类、单位和证据引用必须保留。所有新表纳入已有备份、恢复和项目隔离机制。

报告版本在生成时分配固定版本号，全部子表写入和 READY 发布在同一事务中完成。较旧重解析的完成不能替换较新版本；新版本失败时旧 READY 版本仍可阅读。重新解析产生新版本并保留旧版本，记录解析规则和来源文件指纹。

新表必须先加入 `database.go` 的表名前缀重写白名单；先通过离线 SQL 重写测试证明每张新表使用隔离前缀，才能运行数据库集成测试。备份扩展 `admin.go` 的全部表、列及关联/项目归属校验。恢复 READY 结构化版本时保留其指标和证据元信息；在途任务清除旧租约再恢复。现有备份不自动包含 MinIO 原件，异机恢复后若原件不存在，结构化报告仍可阅读，但原件下载和重新解析明确不可用，不把 MySQL 备份宣传成原件完整备份。

## 统计与日志规则

- CSV 使用标准解析器，支持引号、逗号、UTF-8 和多行字段，不以字符串拆行代替 CSV 解析。
- 对 JTL 必需列和数值作校验。空文件、损坏文件、不支持的格式、无有效样本、缺失日志和部分结果均有单独状态；未知值返回空值，不能伪装成 0 或 100% 成功。
- 跨执行节点先汇总样本或可合并的延迟分布，再计算总百分位，不平均各节点的 P95/P99。
- 百分位保存计算方式和精度。实现使用有界内存的分布统计，并用固定样本验证分位结果；页面对近似结果明确使用“约”及口径说明。P95/P99 目标判定直接使用原始样本中不超过该目标阈值的精确条数，不使用近似分位值作临界值判定；新的评审标准需要重新读取原件以获得准确计数。
- 平均执行速率为 `样本数 / (最大样本结束时间−最小样本开始时间)`；零时长返回空值。时间图保持时间顺序及真实空档。延迟、时间和流量统一单位，不混用秒和毫秒。
- 每个报告保存 `sample_scope`。普通采样和事务采样分别统计，不能把事务及其子请求同时计入总体执行数。结合冻结脚本的事务配置和可核实的 JTL 特征分类；无法可靠区分时使用“采样记录”口径，并禁止生成“请求达标”的结论。列表、时间趋势、步骤表、对比和目标判断采用同一已声明范围。
- 普通采样仍可能包括初始化和脚本步骤。页面使用“接口/步骤执行次数”，不把它等同于订单数、会话量或用户数。
- `success=false` 的断言失败也计入失败，即使 HTTP 状态是 200。没有业务断言时，不声称业务内容已验证正确。
- 不将 JTL 中单个节点的 `allThreads` 当成整个集群的真实并发数；配置值、观测值和缺失值分开。
- 日志记录来自压测端 JMeter/runner。可展示连接超时、响应超时、断言失败、远程执行异常等事实；缺少被测应用和中间件证据时，不宣称 Redis、数据库或 JVM 是根因。
- 所有持久化文本均先脱敏再限长，包括 JTL 标签、响应消息、线程名、URL、聚类键、规则结论、解析器错误和日志摘要；默认不存请求/响应正文、请求头及完整 URL 查询值。Cookie、Token、密码、Authorization 以及任务中已知敏感值不进入报告摘要、图表、搜索索引或 AI 扩展数据。解析失败不回显原始坏行，原件继续走既有鉴权下载。

## 每次压测的目标

创建任务时可填写：最低每秒执行数、最低成功率、95% 请求最大耗时；可选 99% 请求最大耗时、最短有效测试时间。字段全部可留空。

目标是独立业务字段，不作为 JMeter 的执行参数发送给节点。创建任务时与环境、脚本、集群、数据集一起保存快照，并参与任务幂等校验。

判定结果：

- 未设置目标：展示实际数据，标记“未设置验收标准”。
- 数据充分且目标全部满足：标记“达到本次目标”，逐条列出目标和实际值。
- 数据充分但有目标未满足：标记“未达到本次目标”，指出具体差距。
- 非 COMPLETED（包括 FAILED、STOPPED、INTERRUPTED）任务，或 JTL 缺失、校验失败、无有效样本、存在坏行、目标所需字段不可用、样本口径不能确认、执行节点覆盖不能确认时：标记“数据不完整，暂不能完整评估”，保留可用事实，不显示绿色通过。只有文件下载完整、JTL 解析有效、所需节点和统计口径均可确认且目标字段可用，才认为目标判定的数据充分。

日志缺失单独展示为证据缺口；三个归档文件齐全并不等于被测节点数据已齐全。记录实际观测节点和覆盖未知原因，无法确认所有选择节点参与时不显示整体绿色。缺失日志时不宣称日志“无异常”，也不将空日志解释为没有问题。

不从一次固定负载压测推断最大容量或大促可保障量。未在压测前配置的目标，不在后台静默补成默认门槛。对历史任务如需补充标准，必须显式操作并保存新的评审版本，标注标准是测后补充；原始任务与旧判定不被覆盖。

## 报告页面

沿用控制台可选主题，做轻快、留白清楚、以结论为入口的中文页面；先展示易懂结论，再提供技术明细。

1. 报告列表：当前项目的历史报告、生成状态、测试环境、执行时间、是否设置目标及结果。支持搜索和筛选，进入单次报告。
2. 本次结论：一段事实概述、目标判定、环境/脚本/节点与测试时间，以及数据是否完整。只有证据充分才给出明确达标结论。
3. 核心数字：执行次数、成功率、每秒执行数、95% 请求在多久内返回。每个术语有直接解释，时间优先用秒和自然语言展示。
4. 目标对照：目标、实际、是否满足与说明，避免只用红绿颜色表达结果。
5. 过程趋势：测试期间执行量、耗时、失败变化；图表有时间范围、单位和无数据状态。
6. 哪些步骤需要关注：按失败或慢请求排序的步骤表，可查看数量、耗时、失败类型和对应日志证据。
7. 问题与建议：首版基于规则和事实生成；区分“已观察到”与“需要进一步确认”。不虚构 JVM 或中间件指标。
8. 数据与证据：原始文件下载、解析版本、数据覆盖及缺失情况；未来指标来源以相同结构接入，尚未接入时清楚标记。

任务详情的大弹窗增加“压测报告”入口或页签，详情中可查看报告进度并进入报告。独立报告入口支持长内容阅读，避免任务列表变成超长详情页。

已有多次压测对比需求在此数据模型中保留：首版支持选择两份结构化报告查看核心指标差异，明确显示环境、脚本和负载差异，不将不同条件的结果直接解释成性能提升或下降。

## API 边界

- 新报告接口使用 `/api/pressure-reports`，与旧 HTML 报告分开。
- 提供列表、单份报告、步骤/时间序列/问题查询、明确的历史任务生成与重新解析入口；大列表分页，不一次返回全部日志。
- 任务创建接口增加可选的报告目标字段；报告只使用冻结目标或明确新增的评审版本。
- 各查询、重试、文件入口和对比均校验项目归属。只消费该任务已登记的对象引用，不接受任意下载 URL。
- 预留带 `schema_version`、`source_kind`、单位和证据引用的指标/结论写入契约，后续 AI/JVM/中间件接入无需改变核心报告表的含义。
- 首版不配置 AI 密钥、不自动向外部模型发送文件，不对被测集群新增监控采集或业务请求。

## 验证与发布

采用定向验证：解析器固定样本、CSV 边界、失败断言、百分位口径、重复回调、断点重试、文件篡改、缺失/空文件、目标判定、项目越权、敏感值脱敏、版本隔离及原始文件仍可下载。

前端覆盖报告列表、无目标、未达标、缺数据、解析失败、目标解释、日志证据和重新解析；验证桌面和 390px 窄屏。详情弹窗额外验证概览/原始文件/停止入口、ESC、嵌套停止弹窗和内部滚动。

联调优先使用离线 fixture、完全隔离的测试数据表和 mock API。当前另一主会话正在用户授权的 QA 单用户联调，不重启或部署 home 服务，不运行任何业务压测，不读取或复制其敏感凭证。

实现完成后由既有主会话统一审查与发布；用户的报告需求与任务详情弹窗改动均纳入本次清单。
