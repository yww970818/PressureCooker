# 数据库迁移治理实施计划

**目标：** 将启动建表和零散补丁提取为独立 schema 模块，使空库和既有库按版本升级，旧报告缺列得到安全补齐。

**架构：** `manager-go/internal/schema` 使用声明式、冻结的迁移目录与明确的 Migration/Column/Index 类型。每个命名空间使用专用 SQL 连接持有 MySQL 命名锁，记录版本、定义校验和、状态、原始缺列计划及完成时间。DDL 不假设事务回滚；失败保留 APPLYING，重启按原计划恢复，完成后才标记 APPLIED。已完成版本不重复执行；未知新版本、缺失前序版本及定义漂移拒绝启动。

**技术栈：** Go/database/sql、现有 MySQL driver；不添加运行依赖，不变更 API/执行协议。

## 约束

- 保留所有协作修改；只做本地测试/构建，不部署、不启动真实业务压测。
- 原表名、项目默认值、索引、JSON/密文和导入导出格式保持兼容。迁移账本属于运行库结构，逻辑业务备份不导出/导入该账本。
- 已存在的类型投影值不覆盖；仅对迁移首次计划中缺失的列做 JSON 回填，失败后同一计划可重复完成。
- 多实例共用同库同前缀锁，不同前缀隔离。连接池仅一个连接时也能迁移；锁等待、SQL 和清理均有限期。
- 不自动删除列、降级或重放已完成版本；后续变更新增迁移文件，禁止修改已发布版本。

## 复核重点

1. 连接取消/失败后命名锁必须释放或物理连接丢弃，不能随连接回池。
2. 新增列和回填之间退出，重试仍须知道哪些列原先缺失；不得覆盖此前已存在的投影。
3. 历史 READY JSON、加密工作区及任务/attempt 标识不得重写；缺少指标时保持既有默认/NULL 语义。
4. 逻辑备份恢复到空库时运行当前迁移，而不是携带旧数据库的版本账本。
5. 全部 SQL/元数据查询遵守前缀隔离；迁移错误不得回显原始 SQL、JSON、地址或凭据。
